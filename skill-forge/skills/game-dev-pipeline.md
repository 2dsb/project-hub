# 游戏化应用开发管线

**元技能**：从概念到上线的 12 步完整开发管线。适用于任何带游戏化机制的 UI 应用——项目管理系统、学习工具、习惯追踪器等。v6.2 (project-hub 游戏化桌面应用) 是本管线的首个完整验证案例。

## 离线

**我的职责**（不在对话时）：

如果脑子里冒出一个"我想做一个 XX 游戏化应用"的想法，先回忆这个管线：

1. 概念 → 2. GDD(+skill审查) → 3. 视觉方向 → 4. 核心原型 → 5. 技术方案(含跨切面设计) → 6. 垂直切片(含API验证) → 7. 完整生产 → **[7.5. 数据源审计]** → 8. 音效设计 → 9. 新手引导 → 10. 打磨(含响应式+无障碍) → 11. 试玩测试 → 12. 上线运营

然后问自己：**我现在在哪一步？下一步是什么？**

不需要背下来。关键信号：
- 想"开始写代码了" → 检查是否跳过 3-6
- 觉得"差不多做好了" → 检查是否跳过 7.5、8-11
- 核心循环没验证过 → 不能进完整生产
- 数据文件有内容但 UI 看不到 → 必须先修数据缺口再做打磨

## 在线

- 用户跳跃式推进（如从 spec 直接问"怎么实现"）

## 12 步管线（含 v6.2 实战修正）

### 1. 概念
**产出物**：一句话概念陈述（给谁用，解决什么问题，核心机制是什么）

**关隘**：三秒讲给没听过的人，能不能听懂？

**v6.2 案例**："将 project-hub 的所有 markdown 数据封装为游戏化桌面 GUI，日常操作无需阅读源文件；AI 对话作为搭档嵌入应用"

### 2. 产品规格书 (GDD)
**产出物**：完整功能清单 + 交互逻辑 + Wireframe + 数据映射表 + 边缘情况 + 游戏机制数值表

**关隘**：一个独立的开发者拿这份文档，能不能做出一样的东西？

**v6.2 实战修正**：
- **Skill 审查子步骤**：GDD 完成后，用领域 skill 做多轮审查。v6.2 的规格书经过了 game-ui-design、gamification-loops、build-dashboard 三轮审查，在设计阶段就捕获了色盲可访问性、通知优先级队列、渐进信息披露等问题。审查不是一次性的——规格书更新后（如补充 v6.1 可视化集成）应再次审查。
- **GDD 是活文档**：实施过程中会发现规格书的缺口（v6.2 发现了 7 个 v6.1 覆盖缺口），GDD 应在开发过程中持续更新，而不是"冻结后不再改动"。每次更新后记录变更原因。
- **数据映射表是 GDD 最重要的部分**：每个 UI 元素 ← 数据源 ← 字段 ← 更新触发。这张表越完整，完整生产阶段越顺利。

### 3. 视觉方向
**产出物**：风格指南（配色/字体/间距/圆角/阴影）+ 2-3 张关键页面高保真 mockup

**关隘**：用户看 mockup 的第一反应是不是"我想用这个"？

**v6.2 实战修正**：
- 游戏化应用的颜色方案需要**双重编码**（颜色+形状），8% 男性有色觉障碍。v6.2 的优先级使用 ◆critical/▲high/●medium/○low，系统状态使用圆/三角/八角，不单独依赖颜色。
- CSS 变量体系应在视觉方向阶段就定义好，避免生产阶段重复写颜色值。

### 4. 核心循环原型
**产出物**：最小可感循环的可交互原型——只包含核心激励路径（完成任务 → 获得 XP → 升级/解锁 → 庆祝反馈 → 再来一次）

**关隘**：跑完一个循环后有没有"再来一次"的冲动？如果没有，GDD 里的数值和机制需要重新设计。

**不可跳过**。

### 5. 技术方案
**产出物**：技术选型（框架/渲染/数据流/AI 通信）+ 架构图 + 不可行性排除 + **跨切面组件设计**

**关隘**：团队里每个人都知道自己负责的部分怎么和他人对接？

**v6.2 实战修正**：
- **跨切面组件必须在技术方案阶段设计**：AI 面板（常驻右侧，所有页面共享）、键盘快捷键（全局 Ctrl+1~7、Ctrl+`）、状态管理（React Context）、响应式策略（三档断点）。这些组件触碰每一个页面，如果在完整生产阶段才加，改造成本极高。
- **API 层设计**：如果数据源是 markdown 文件，API 层（vite 插件）决定了哪些数据对前端可见。v6.2 的教训：API 只返回了 frontmatter 而丢弃了 body，导致 daily 的全部正文内容在 UI 中不可见。API 设计时应明确：每个端点返回什么字段？body 是否包含？

### 6. 垂直切片
**产出物**：一个功能从头到尾完整打穿（markdown 数据源 → API → 前端组件 → 交互反馈 → 写回 markdown），展示端到端的完整链路

**关隘**：这条链路上每一个环节都工作正常，没有断裂？

**v6.2 实战修正**：
- 垂直切片必须包含 **API 层验证**：确认 API 返回的数据字段与 GDD 数据映射表一致。v6.2 的垂直切片（Dashboard + Sidebar）验证了 XP/等级/连胜的核心循环，但没有检查 daily body 是否返回。
- 垂直切片通过后，GDD 数据映射表中已验证的字段标注 ✅，为完整生产提供参考。

### 7. 完整生产
**产出物**：按 GDD 铺设剩余所有功能和页面

**关隘**：每个页面数据映射正确？每个交互都有响应？

**v6.2 实战修正**：
- 完整生产完成后，**不要直接进入打磨**。先做数据源审计（7.5）。

### 7.5. 数据源审计（v6.2 新增步骤）

**产出物**：数据覆盖率报告——每个 markdown 数据文件的每个区段，是否在 UI 中可见？

**方法**：
1. 列出所有数据源文件（projects/*.md, daily/*.md, ideas/*.md, skills/*.md, visualizations/*.md, INDEX.md, profile.md 等）
2. 对每个文件：读取完整内容 → 对比 API 返回的字段 → 对比 UI 组件实际渲染的内容
3. 标记缺口：文件中有 / API 返回了 / UI 显示了

**v6.2 发现的典型缺口**：
- Daily 文件：API 只返回 frontmatter（4 个字段），body 中的晨间回顾/当日状态/日程表/项目推进/已完成/想法与笔记全部不可见
- INDEX.md：Dashboard 自算数据，不读取"本周焦点""风险提醒""最近动态"区段
- Demands：已移除（v6.6 用项目层级替代）
- Skill body：API 只返回 frontmatter，执行指南正文不展示
- Visualizations：3 张 Mermaid 图表文件存在但未嵌入任何 UI 组件

**关隘**：每个数据文件的内容都能在 UI 的某个地方看到？如果某个区段故意不展示，理由是什么？

**不可跳过**。这是 v6.2 开发中投入产出比最高的步骤——发现的所有缺口都是"数据已经有了，只需要打通最后一公里"。

### 8. 音效设计
**产出物**：关键事件的反馈音效（升级/成就解锁/XP 增长/连胜更新/错误/提醒），含关闭开关

**关隘**：静音状态下体验不降级？音效类型不混用（升级≠成就≠普通任务完成）？

### 9. 新手引导
**产出物**：首次启动时的引导流程——第 1 分钟让用户完成一个核心循环，然后自己探索

**关隘**：一个新用户不看文档，5 分钟内能不能完成"做一件事 → 看到反馈 → 理解这个系统在干什么"？

**v6.2 实战修正**：
- v6.2 的 Onboarding 组件是 5 步引导（localStorage 记录完成状态）。正常流程走完后用户知道 7 个页面在哪、AI 面板怎么打开。
- 引导不应只介绍"功能在哪"，更应让用户完成一次"操作→反馈"闭环。

### 10. 打磨
**产出物**：动画曲线校准 + 无障碍完整 + 键盘导航 + 色盲模式 + **响应式三档** + 所有 loading/error/empty 状态 + 焦点视觉指示器

**关隘**：关掉所有"华丽"动画，操作效率有没有降？Tab 键盘能不能走完全部功能？

**v6.2 实战修正**：
- **响应式布局在打磨阶段统一做**：不是在每个组件开发时分别考虑响应式，而是在所有页面完成后，用 CSS 媒体查询统一处理三档断点（≥1200px 三栏 / 768-1199px 两栏 / <768px 单栏）。v6.2 的响应式是通过修改 App.module.css + Sidebar.module.css + AIPanel.module.css 三个文件完成的，改动集中且可控。
- **打磨清单**（v6.2 实际执行）：
  - 页面切换动画（framer-motion 0.15s 淡入）
  - 进度条填充动画（0.5s ease-out）
  - 升级 Toast（顶部滑入 + 弹簧缓动 + 4s 自动消失）
  - 成就卡片悬停效果
  - AI 面板折叠/展开过渡
  - 侧栏移动端滑入动画
  - 空状态引导文字（文献笔记/永久笔记/Ideas 三态）
  - 焦点指示器（2px 蓝色外框 + 发光）

### 11. 试玩测试
**产出物**：自己使用 N 天后的调参记录——XP 数值、升级 S 曲线斜率、成就触发频率、连胜弹性合理性 + **数据源审计发现的缺口修复验证**

**关隘**：核心指标（日均 XP、升级间隔、成就解锁率、连胜中断率）是否在健康区间？**7.5 步骤发现的数据缺口是否已全部修复？**

**不可跳过**。

**v6.2 实战修正**：
- 试玩测试不仅验证数值平衡，更要验证"信息完整性"——数据审计发现的缺口修复后，在真实使用中确认每个信息都能被用户看到。
- v6.2 试玩发现了响应式布局缺失、备份按钮未实现、AI 面板命令不完整等问题，这些是自动化测试无法捕获的。

### 12. 上线运营
**产出物**：持续运行的系统 + 版本迭代循环（collect → review → execute → version_cut）

**关隘**：日常使用中自然产生新需求，每个版本解决真实问题而非臆想需求？

## 补充规则

- **不可跳过**：核心原型（4）、数据源审计（7.5）、试玩测试（11）。跳过 4 的风险是做了一个没人想用的东西；跳过 7.5 的风险是"数据已经有了但用户看不到"——这是最隐蔽的质量问题；跳过 11 的风险是数值偏差让激励系统适得其反。
- **可合并**：音效设计（8）+ 打磨（10）在小项目中可合并为"收尾阶段"；概念（1）+ 视觉方向（3）在个人项目中可合并为"设计阶段"
- **视觉方向（3）和核心原型（4）可并行**：原型可以用低保真 UI 跑通，视觉方向同时探索
- **GDD Skill 审查**：步骤 2 完成后、步骤 5 开始前，至少用 2-3 个领域 skill 审查 GDD。每个 skill 会发现不同维度的问题（UI skill 关注可访问性、游戏化 skill 关注激励平衡、仪表盘 skill 关注数据展示）
- **数据映射表是贯穿全管线的契约**：从步骤 2 的 GDD 定义 → 步骤 5 的 API 设计 → 步骤 6 的垂直切片验证 → 步骤 7 的完整生产 → 步骤 7.5 的数据源审计。每一步都以它为参考
- **本管线是通用框架**，具体项目可以根据规模和团队大小裁剪，但裁剪决策本身需要被记录（为什么跳过某步）
