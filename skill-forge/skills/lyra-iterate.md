# Lyra 迭代优化器

**元技能**：当一次 Lyra 优化不够好时，自动驱动多轮迭代优化直到收敛。封装了"DETAIL using Deepseek V4 pro[1m] 接入 Claude Code，使用 max effort"的默认配置，消除每次手动调用 Lyra 的重复劳动。

## 离线

**我的职责**（不在对话时）：

当我有一个需要优化的提示词时，先判断它是"一次就够"还是"需要迭代"：

- **一次就够**：简单翻译、格式调整、单段润色 → 直接用 `/lyra` 走 BASIC 模式
- **需要迭代**：复杂任务描述（游戏开发管线、自主 Agent 系统、多步骤工作流）→ 启动本 skill

关键信号：
- 第一版 Lyra 输出后，读一遍觉得"还行但不够好" → 启动迭代
- Lyra 输出太长、太散、AI 会误解 → 需要迭代收紧

迭代的终点判断：
- 连续两版之间的改动 < 20% → 趋于收敛，停止
- 提示词已经能直接复制执行 → 达到目标，停止
- 超过 7 轮仍未收敛 → 问题可能不在提示词本身，停止并分析根因

## 在线

### 触发时机

AI 在以下任一情况时启动本 skill：

- 用户说"继续优化""再来一轮""还是不够好"——在 Lyra 输出后的对话中
- 用户直接调用 `/lyra-iterate` 或说"用 lyra-iterate"
- 用户提供了一段待优化的提示词，且满足以下任意两条：(a) 段落数 ≥ 3（以空行分隔），(b) 包含 ≥ 3 个独立步骤/阶段，(c) 包含 ≥ 2 种技术约束（如平台/模式/输出格式/角色设定）
- Lyra 刚输出一版优化结果，用户在 3 条消息内又调用了 `/lyra`

### 默认配置

所有迭代轮次统一使用以下配置：

- **平台**：Deepseek V4 pro[1m] 接入 Claude Code
- **模式**：DETAIL（每轮先诊断再优化，不是简单改写）
- **强度**：max effort（不缩略、不跳过、不假设）

### Steps

- order: 1
  action: "确认迭代起点。边界检查：如果用户未提供提示词或内容 < 20 字符 → 提示'请先提供需要优化的提示词内容'，停止。正常流程：如果用户提供了新的原始提示词 → 先调用 Lyra 生成 v1，skill_args 格式：'DETAIL using Deepseek V4 pro[1m] 接入claude code，使用max effort 待优化的提示词：[完整提示词内容]'。如果用户已有 Lyra 输出版本 → 以当前最新版本为起点。读取当前提示词内容，记录版本号（v1 或用户已有版本号）和字符数，写入迭代日志。"
  note: "第一轮优化前必须先明确'优化什么'——如果用户只说'继续优化'但没有指定方向，先问：上一版哪里不满意？太长/太散/不具体/缺约束/风格不对？拿到方向后，将方向映射为 lyra 关键词（见补充规则中的'反馈方向→lyra指令映射表'），追加到 skill_args 中。"
  execute_skill: "lyra"
  skill_args: "DETAIL using Deepseek V4 pro[1m] 接入claude code，使用max effort"
  on_failure: "prompt"
  on_failure_note: "Lyra 调用失败时，告知用户失败原因，询问'是否改为手动优化（AI 自行逐步优化，不依赖 Lyra）？'。若用户同意 → 跳过 Lyra 调用，AI 直接按诊断→优化流程生成 v1，标记为'手动优化'，继续进入 Step 2。"

- order: 2
  action: "评估收敛状态，并向用户展示确认。对比当前版本与上一版本：1) 结构变化（段落重组/拆分/合并比例）2) 新增内容占比（全新段落比例）3) 删除内容占比（被砍掉的比例）4) 核心指令的变化程度（核心指令 = 提示词中描述'AI 必须做什么'的约束性语句，通常以'必须''不得''只做''输出格式为'开头）。收敛判定：取 4 项中的变化率最大值，若 < 20% 且无核心指令新增 → 报告收敛，建议停止。同时检查其它两个终点：2) 提示词是否已可独立执行（所有步骤有明确输入/输出、无上下文依赖、无'上一版''同上'等引用）→ 若是，报告达到目标；3) 当前轮数是否 ≥ 7 → 若是且未收敛，报告'问题可能不在提示词本身'，建议分析根因。将评估结论展示给用户，等待用户确认'继续迭代'或'停止'。继续则进入 Step 3，停止则跳至 Step 4。"
  note: "收敛不等于'完美'——收敛意味着继续优化边际收益急剧下降。此时应建议用户用当前版本实际测试，根据 AI 的执行反馈再针对性优化。第一轮（尚无上一版）时跳过收敛评估，直接展示 v1 版本并询问用户反馈方向。"
  execute_skill: null
  skill_args: {}
  on_failure: "continue"

- order: 3
  action: "执行迭代轮次。每轮：1) 确认本轮优化方向（用一句话概括，如'本轮目标：精简字数'），如果用户在前一轮给了反馈方向，本轮优先针对该方向（使用补充规则中的映射表追加 lyra 指令）2) 调用 Lyra（Skill 工具，skill='lyra'，args 必须每次完整传入当前版本的提示词文本 + 默认配置 + 针对性方向指令，不能只传版本号或文件路径）3) 记录新版本号（v1→v2→...）4) 对比与上一版的差异并记录。本步骤执行完毕后，返回 Step 2 重新评估收敛，循环直到 Step 2 判定收敛或达到 7 轮上限。注意：第 5 轮后若未收敛，在返回 Step 2 时主动标记'已超过甜点区间，建议评估边际收益'。"
  note: "轮数计数由本步骤负责（通过版本号递增追踪）。每轮 Lyra 调用失败时的降级策略：记录该轮为'手动优化'，AI 自行按当前反馈方向调整提示词，生成新版本号，继续循环。连续 3 轮 Lyra 调用失败 → 转为全手动模式并告知用户。"

## 补充规则

### 反馈方向 → Lyra 指令映射表

当用户给出不满意方向时，对应追加到 lyra skill_args 中的补充指令：

| 用户反馈 | 追加到 args 的指令 |
|---------|-------------------|
| "太长" | "目标是删减约 30% 字符数，保留核心指令，合并相关内容到同一段落" |
| "太散" | "重点关注结构紧凑性，将相同主题的指令合并到同一段落，减少独立散句" |
| "不具体" | "每条指令需有可量化标准或具体示例，避免'适当''必要时'等模糊词" |
| "缺约束" | "为每个步骤添加明确的边界条件（输入条件/输出标准/不做什么）" |
| "风格不对" | "调整语气和格式风格，参考用户提供的期望风格样本" |
| "AI 会误解" | "重写歧义指令，每条只表达一个明确动作，添加'不是你理解的 X，而是 Y'的澄清" |

### 其它规则

- **用户反馈优先**：如果用户在迭代中途给了具体反馈，下一轮必须优先处理该反馈。使用映射表将反馈转为 lyra 指令，追加到本轮 skill_args 中
- **Lyra 调用必须用 Skill 工具**：不要手动写 Lyra 风格的输出，必须通过 Skill 工具调用 `lyra` skill，确保真正走 Lyra 的 4-D 流程
- **减法优先于加法**：当两轮之间选择困难时，优先选更短的版本。超过 800 字的提示词在多次执行中，AI 对同一条指令的理解一致性会下降。优先保持最终版本在 500 字以内
- **收敛即停止**：不要为了凑轮数而继续优化已收敛的提示词。3-5 轮是甜点区间，超过 7 轮通常是结构问题而非措辞问题
- **文件化最终版**：最终版本应写入项目目录（如 resources/ 下），方便后续引用和版本对比
- **多次 lyra 提醒**：当 AI 注意到用户在连续消息中多次调用 `/lyra` 优化同一段提示词时，主动建议用户"要不要用 lyra-iterate 一次跑完多轮迭代？"
- **中途改方向**：每轮迭代开始前用一句话确认当前优化方向。如果用户给出了与上轮不一致的反馈方向，优先使用最新的方向
- **Lyra 调用失败降级**：某一轮 Lyra 调用失败 → 记录该轮为"手动优化"，AI 自行按当前方向调整提示词，继续循环。连续 3 轮 Lyra 调用失败 → 转为全手动模式并告知用户
