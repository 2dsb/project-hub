# 联系人关系维护

**触发条件**：用户说"帮我查一下联系人""新增联系人""维护提醒""谁认识/谁会""匹配资源""联系人管理"，或在 AI 浏览到与某联系人兴趣匹配的内容时主动触发提醒。

**核心原则**：维持联络不靠泛泛的问候，靠"记得对方在意什么"（投其所好）。系统帮你记住每个人的兴趣和动态，你来决定何时、以什么方式触达。

## 离线

**用户职责**：

1. **维护联系人数据**：在 `entities/` 目录下为每个联系人创建/更新 Markdown 文件（格式见下方"联系人实体 schema"）。
2. **记录互动**：每次有意义的联络后，在联系人文件中追加一条 `## 互动日志` 条目（日期 + 一句话内容），AI 才能判断"上次联系是什么时候"。
3. **执行实际联络**：AI 提供提醒和建议，但发消息、打电话、转发内容是用户的事。AI 不替你做人际互动。
4. **更新兴趣点和动态**：当你了解到联系人的新兴趣、新动态、新需求时，更新对应字段。AI 的匹配能力直接依赖这些数据的时效性。
5. **分级维护**：按"核心关系 / 一般关系 / 弱关系"对联系人分级，不同级别投入不同精力——核心关系主动挖话题，一般关系生日+偶发投喂，弱关系保持可见但不过度投入。

### 联系人实体 Schema

每个联系人在 `entities/` 下以一个 `.md` 文件存储：

```yaml
---
name: "姓名"
phone: "电话号码"
relationship: "与我的关系（如：高中同学 / 前同事 / 导师）"
identity: "身份/职业"
birthday: "MM-DD"
interests: ["兴趣1", "兴趣2", "关注领域"]
recent_updates: ["近期动态1", "近期动态2"]
resources: ["可调动的资源/技能1", "资源2"]
needs: ["当前需求1"]
maintenance_tier: "core"  # core / general / weak
last_contact: "YYYY-MM-DD"
tags: ["标签1"]
---
```

**字段说明**：
- `interests`：对方在意什么——用于"投其所好"的内容匹配
- `recent_updates`：对方最近在做什么/关心什么——用于自然话题触发
- `resources`：对方能提供什么（技能、人脉、信息渠道、物质资源）——用于需求匹配
- `needs`：对方当前需要什么——用于机会分发和三赢撮合
- `maintenance_tier`：维护投入级别
- `last_contact`：上次有意义的联络日期（非群发祝福）

## 在线

### 触发时机

- 用户说"查一下 [某人]"或"谁认识 [领域/技能]"或"谁有 [资源]"
- 用户说"新增联系人 [姓名]"或"更新 [某人] 的信息"
- 用户说"维护提醒""该联系谁了""有什么联络机会"
- 用户说"匹配资源 [需求]"或"谁需要 [某物/某技能]"
- AI 在对话中浏览到与某联系人的 `interests` 匹配的内容时，主动提示"要不要转发给 X？"
- 每日 `start` 流程中检测到当日有联系人生日或待跟进事项

## 补充规则

### 资源可视度（双向信息不对称）

- **我的问题**：我能调动的资源（直接+间接）别人看不到 → 别人不会主动找我。解决：AI 可以在合适的时机帮用户梳理"你目前可调动的资源总览"（汇总所有联系人的 `resources`），让用户对自己的资源网络有全局感知。
- **别人的问题**：很难判断别人有多少隐藏资源。解决：在添加/更新联系人时，AI 主动追问"TA 还可能认识什么人？TA 还有什么你没写的技能？"，尽可能补全 `resources` 字段。
- **撬动二级资源**：A 帮不了我但 A 的朋友 B 可以 → 关键不是有没有 B，而是 A 是否愿意为我打开他的人脉。这需要 A 对我有足够信任 + 对我需求的清晰理解。AI 在匹配二级资源时，标注信任前提——"这个路径需要 A 对你足够信任，才会愿意引荐"。

### 与 daily 的集成

每日 `start` 流程中，AI 应自动检查：
- 当日是否有联系人生日 → 写入 daily 提醒区
- 是否有超期未联系的核心关系（超过阈值） → 写入 daily 建议区
- 是否有待跟进的承诺/回复 → 写入 daily 提醒区

### 隐私边界

- 联系人数据是高度敏感的个人信息。AI 在展示联系人信息时，区分"可公开"和"仅自己可见"的内容——`resources` 和 `needs` 字段属于敏感信息，在对外场合（如生成可分享的报告）时默认不展示。
- 联系人文件存储在本地 `entities/` 目录，不通过任何外部服务传输。

### 维护投入分级

| 级别 | 主动挖掘话题 | 生日提醒 | 定期联络阈值 | 内容投喂频率 |
|------|------------|---------|------------|------------|
| core | 是 | 是（提前3天预警） | 2 周 | 看到匹配内容即提醒 |
| general | 否 | 是（当天提醒） | 1 个月 | 看到高度匹配内容提醒 |
| weak | 否 | 否（不提醒） | 3 个月 | 不主动提醒 |

### 边界情况处理

- **联系人目录为空**：提示用户"还没有联系人记录，要创建第一个吗？"并引导按 schema 填写。
- **搜索无匹配结果**：告知用户"没有直接匹配的联系人"，然后自动尝试二级资源推断（通过已知联系人的 `identity` 推断其可能的人脉圈）和模糊匹配（同领域/相关技能）。如仍无结果，建议"要不要新增一个相关领域的联系人？"
- **用户口头描述联系人（未写文件）**：AI 先按描述执行匹配/查询，然后提醒"这个联系人的信息只在对话中，要帮你写入文件吗？"
- **last_contact 为空（新联系人从未联络过）**：按"从未联络"展示，不计入超期统计。
- **用户说"先记一下"但信息不完整**：不阻塞——先保存已有字段（姓名+关系是底线），其余标记为待补充，下次查询该联系人时提醒"还有 N 个字段待补充"。
