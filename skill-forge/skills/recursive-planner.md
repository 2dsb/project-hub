# 递归计划执行器

**元技能**：当 general-task-flow 无法处理的复杂任务时，驱动 5 个独立子智能体（C/A/B/D/E）按递归层级制定计划并执行。不依赖用户的专业判断力——每一步产出都经过"创造→严苛审核"闭环。

依赖：`general-task-flow`、`find_skills`（需 AI 在使用本 skill 前确认已安装）

## 离线

**我的职责**（不借助 AI 时）：

### 何时使用本 skill

当以下 ≥ 2 个条件成立时，应认真考虑启动 recursive-planner：

1. 我对该领域几乎一无所知，无法有效审查 AI 产出
2. 任务涉及 ≥ 3 个不同子领域，需要不同专业方法论
3. 单次 AI 对话显然无法完成
4. general-task-flow 执行时，AI 建议升级到 recursive 模式

### 何时不该使用

1. 我已是该领域专家——我能自己审查 AI 产出，不需要多层审核
2. 简单任务——`/lyra` 或 general-task-flow 能搞定
3. 一次性问答——没有"产出"需要交付，只是咨询

### 使用前的心理准备

1. **信任流程而非相信自己**：这个 skill 的设计目标就是"你不懂也能出高质量结果"。审核是 B 和 E 的职责，不是你的
2. **C 向你提问时，认真回答**：这是整个流程中你唯一的输入窗口。模糊的需求进去，模糊的计划出来
3. **不要跳过审核环节**：如果 AI 建议跳过某步审核（"这个很简单不用审了"），拒绝。B 和 E 的严苛是质量保障
4. **计划通过后再实施**：这是本 skill 的核心原则。计划没通过 B 的审核，绝不让 D/E 执行

## 在线

### 触发时机

AI 在以下任一情况启动本 skill：

1. 用户直接说"用 recursive-planner"或 `/recursive <任务描述>`
2. 正在执行 general-task-flow 时，AI 判断任务复杂度超出其处理能力（≥ 3 个子领域 OR 计划步骤 ≥ 8 步 OR 用户明确表示"我不懂这个领域"），主动建议"这个任务建议升级到 recursive-planner 模式"
3. 用户描述了一个任务，且满足以下任意两条：(a) 任务涉及 ≥ 3 个不同专业领域 (b) 用户明确表示对该领域不了解 (c) 任务的最终产出需要经过多轮审核才能保证质量 (d) 任务预计需要 ≥ 5 次独立 Agent 调用来完成

### 核心原则

1. 计划先行，再实施。计划有问题，实施没有价值
2. 每一层级的产出都经过"创造→严苛审核"闭环
3. 审核者权力 > 同层制定者/监督者；上层权力 > 下层
4. 自动化管线 + 文件持久化，用户随时 `cat` 查看进度

### 5 个独立子智能体

所有子智能体通过 Agent 工具以独立实例运行（各自拥有独立上下文）。通信通过磁盘文件完成。

#### C — 需求澄清者

- **职责**：与用户对接，逐轮澄清需求。C 不仅是初始澄清者，也是**全程活跃**的"人机接口"——在 A/B/D/E 执行过程中**持续**监控状态，过滤并向你传达关键进展，在中途发现需求缺口时主动向你追问。C 从任务开始到结束始终保持活跃，不会"提问完就消失"
- **工作方式**：
  - 每轮向用户提 1-3 个聚焦问题，逐步缩小模糊地带
  - 问题类型：目标澄清（"你想要的最终产出是什么？"）、约束澄清（"有什么硬性限制？"）、优先级澄清（"哪个方面最重要？"）
  - 每次收到用户回答后，将澄清结果写入 `L0-overall-plan/requirements.md`（追加模式，不覆盖）
  - 当 A 或 B 反馈"需求不明确，无法继续"时，C 提取具体不明确的点，转化为问题向用户提问
  - 判断需求足够清晰时，通知 A"需求已就绪，可以开始制定计划"。判断标准（可操作，5 项全部满足才可发出就绪信号）：(a) C 连续 2 轮澄清未提出新问题**领域**（不是新问题本身，而是没有触及之前未覆盖的话题领域）；(b) 累计已完成至少 3 轮问答（确保深度——防止仅 1-2 轮浅层问答后就宣告就绪）；(c) A(n) 在最近一轮 plan-draft.md（已纳入 B(n) 的审核意见后）中未标记"需求不明确"；(d) B(n) 在最近一轮 plan-review.md 中未将"需求不明确"或"用户需求对齐"（第 7 条）列为 REJECT 理由；(e) C 已明确问过"除了我已经问过的问题之外，关于这个任务你是否还有其他需要说明的？"并在最近一轮中收到否定或满意的回应
- **权限**：无决策权，仅收集和澄清信息。无权修改计划或执行结果
- **禁止**：C 不得自行替用户做假设。所有不确定的点必须问

#### A(n) — 计划制定者

- **职责**：在给定层级制定执行计划。极具创造力
- **必读材料**：
  - 上一级传入的 `plan-final.md`（理解本级要完成什么）
  - C 产出的 `requirements.md`（理解用户想要什么）
  - 若有下层 `final-report.md`，读取作为参考
- **方法论**：制定计划前，主动搜索和学习该领域的专业方法论：
  - 行业顶级公司/团队的实际工作流程
  - 该领域专家公认的标准做法
  - 学术文献或行业标准中的最佳实践
  - 使用 `find_skills` 搜索是否有相关的 skill 可辅助
- **工作方式**：
  - 产出 `plan-draft.md`，包含：目标定义、步骤列表（含依赖关系）、每步的验收标准、所需资源/工具
  - 步骤间关系标注：顺序(→)、并行(∥)、条件(if→then→else)、循环(↻)
  - 将计划写给 B(n) 审核
- **工具权限**：可使用已有 skill，可 `find_skills` 搜索，不可私自下载。需下载时报 C，C 向用户请示
- **与 B 的交互**：接收 `plan-review.md`，若为 REJECT → 逐条修改 → 重新提交 plan-draft.md。循环直到 PASS

#### B(n) — 计划审核者

- **职责**：审核 A(n) 的计划。极其严苛。同层权力高于 A(n)
- **审核标准**（每一项必须通过）：
  1. **完整性**：步骤是否覆盖了目标的所有方面？有无遗漏？
  2. **可行性**：每一步在 AI 能力范围内？是否有不可实现的假设？
  3. **方法论正确性**：步骤顺序是否符合该领域的专业实践？参考的行业标准是否正确应用？
  4. **依赖清晰**：步与步之间的依赖关系是否明确？并行步骤是否真的互不依赖？
  5. **验收标准可量化**：每步的"完成"标准是否具体？（"好"不是验收标准；"通过 10 个测试用例"才是）
  6. **风险识别**：是否识别了高风险步骤？有无缓解措施？
  7. **用户需求对齐**：计划是否回应用户在 requirements.md 中的所有关键诉求？
  8. **上下文安全**：计划是否考虑了 AI 上下文限制？是否避免了跨层污染？
  9. **Skill 利用**：A 是否搜索了适用 skill？发现的 skill 是否恰当？A 是否遗漏了本应找到的 skill？（若 A 跳过 skill 搜索 → 直接 REJECT，违反第 9 条）
- **工作方式**：
  - 读 `plan-draft.md`，逐条对照 9 项审核标准
  - 产出 `plan-review.md`：PASS（全部通过）或 REJECT（列出具体修改项，每条引用审核标准编号）
  - REJECT 时，修改意见必须具体——不能写"步骤 3 不够清晰"，要写"步骤 3 缺少验收标准：应该明确写出'通过 10 个测试用例且覆盖率 ≥ 80%'"
- **冲突处理**：若 A(n) 不同意 B(n) 的修改意见 → B(n) 的意见优先。若 A 认为 B 的修改会导致技术问题 → A 可在修改 plan-draft.md 时附加"保留意见"备注，但必须按 B 的要求修改
- **工具权限**：同 A(n)

#### D(n) — 任务监督者

- **职责**：
  - 非叶子节点：接收上级 plan-final.md → 遍历每一步 → 判断每步复杂度 → 复杂则创建子级 A(n+1)+B(n+1)，不复杂则进入叶子模式
  - 叶子节点：组建工人团队，分配任务，初步验收产出
  - **关键改变（v6.3）**：D 不再是"派生子智能体后就撒手不管"。新流程要求 D：总结计划 → 逐步执行 → 对复杂步骤派生子智能体后**等待**其完成 → 与 E **共同审查**子级产出 → 所有步骤完成后 D+E **联合检查**整体完成情况。D 在派生子智能体后必须等待其产出文件（而非立即继续下一步），且 E 必须参与每一层递归的产出审核
- **双重身份**：管理大师 + 该任务领域的顶尖人才 + AI 特征专家
- **复杂度判断**（判断步骤是否需要继续递归）：
  - 该步骤本身可以拆分为 ≥ 3 个独立子步骤 → 复杂，递归
  - 该步骤涉及 ≥ 2 个不同专业领域 → 复杂，递归
  - 工人团队人数超过 3 人 → 复杂，递归
  - **例外条款**：若所有子步骤属于同一领域且重复性强（如"翻译 10 种语言的文档"），即使子步骤 ≥ 3，也应合并为叶子节点而非递归。核心判断依据：每个子步骤是否需要**独立专家知识**。需要不同专家 → 递归；同一专家可完成全部 → 叶子
  - 否则 → 不复杂，叶子节点，直接执行
- **叶子节点 — 组建团队**：
  - 产出 `team-config.md`：列出工人角色定义（每个工人的身份、专业、职责范围）、工人数量（最少 1 人，绝对上限 6 人——若任务需要超过 6 人，应拆分为递归子步骤而非增加工人；每个工人的数量选择需附 1 句理由）、团队协作方式（串行/并行/互相审核）
  - 每个工人必须配置"做该工作最好的已有 skill/工具"（通过 find_skills 搜索）
  - 若需下载新工具 → 通报 C → C 向用户请示
- **叶子节点 — 验收产出**：
  - 读工人产出 → 对照 `plan-final.md` 中的验收标准
  - 产出 `final-report.md`（宽松标准：基本符合验收标准即可通过）
  - 若 E(n) 驳回 → 将 E 的意见转达工人 → 工人修正 → 重新验收
- **权力**：同层权力低于 E(n)。与 E 冲突时服从 E

#### E(n) — 任务审核者

- **职责**：
  - **全部层级审核**：E 的审核范围已从"仅叶子节点"扩展为"**全部层级**"——不仅审核叶子节点的团队配置和工人产出，也审核**非叶子节点**的子智能体产出
  - 审核 D(n) 的团队配置（叶子节点）
  - 审核工人团队的最终产出（叶子节点）
  - 审核子级递归的完整产出（非叶子节点）：当子级 A→B→D→E 完成时，E(n) 对照上级计划验收标准审核子级 final-report.md 及所有产出
  - 每层递归结束时 D+E 联合签署整体完成确认
- **双重身份**：管理大师 + 该任务领域的顶尖人才 + AI 专家
- **审核团队配置**（叶子节点）：
  - 工人数量是否恰当？（太少可能遗漏，太多可能混乱）
  - 每个工人的角色定义是否清晰、不重叠？
  - 工具配置是否恰当？（是否用了最适合的已有 skill？是否遗漏了关键工具？）
  - 产出 `team-review.md`：PASS 或 MODIFY（具体修改项）
- **审核工人产出**（叶子节点）：
  - 对照验收标准逐条验证
  - 检查是否有遗漏、错误、不一致
  - 极其严苛——比 D(n) 的宽松验收标准严格得多
  - 产出 `output-review.md`：PASS 或 REJECT + 具体修正项
  - REJECT 时 → 由 D(n) 转达工人 → 修正 → D(n) 再验收 → E(n) 再审
- **冲突处理**：若 D(n) 不同意 E(n) 的审核意见 → E(n) 的意见优先
- **反复修正不达标**（叶子节点）：同一任务经 3 轮修正仍被 E(n) REJECT → 不是工人的问题，是步骤设计有问题 → E(n) 将 `output-review.md` + 根因分析上报给上级 D(n-1) 和 E(n-1)，建议重新规划该步骤

### 递归执行流程

```
第 0 层（整体计划）:
  1. C 澄清需求 → requirements.md
  2. A(0) 读需求 → 产 plan-draft.md → B(0) 审核
     ↻ REJECT → A(0) 修改 → B(0) 再审核 → ... → PASS
  3. D(0) + E(0) 接管，遍历 plan-final.md 中每个步骤:

     对于步骤 k:
       D(0) 判断复杂度:
       
        复杂 → 递归进入第 1 层:
          4a. 创建 A(1)+B(1) → 制定子计划 → B(1) PASS
          4b. 创建 D(1)+E(1) → 遍历子步骤 → 判断复杂度...
              （继续递归直到叶子节点）
          4c. D(0) **等待** 第 1 层完成 → E(0) **审核** 子级产出
              → PASS 则继续，REJECT 则驳回子级修正
        
        不复杂 → 叶子节点:
          4a. D(n) 组建工人团队 → 写 team-config.md
          4b. E(n) 审核团队配置 → team-review.md
              ↻ MODIFY → D(n) 修改配置 → 再审核 → PASS
          4c. 工人团队执行任务 → 产出
          4d. D(n) 验收（宽松）→ E(n) 审核（严苛）
              ↻ REJECT → 工人修正 → D(n) 再验收 → E(n) 再审
              超过 3 轮仍 REJECT → 上报上级重新规划
          4e. E(n) PASS → D(n) 写 final-report.md → 上报上级

    所有步骤完成后:
      D(0)+E(0) **联合检查** 整体完成情况 → 签署 final-report.md
```

### 通信机制

所有智能体通信通过磁盘文件完成。执行根目录：`<project>/.recursive-planner/`

```
.recursive-planner/
├── state.json                    ← 全局状态树
├── heartbeat.log                 ← 心跳日志
│
├── L0-overall-plan/
│   ├── requirements.md           ← C 的需求澄清记录
│   ├── plan-draft.md             ← A(0) 的计划草案
│   ├── plan-review.md            ← B(0) 的审核意见
│   ├── plan-final.md             ← 通过后的最终计划
│   │
│   ├── step-01-<slug>/
│   │   ├── L1-plan/              ← 若复杂，子计划
│   │   │   ├── plan-draft.md
│   │   │   ├── plan-review.md
│   │   │   └── plan-final.md
│   │   │
│   │   ├── L1-exec/              ← 若不复杂，直接执行
│   │   │   ├── team-config.md    ← D(1) 的团队配置
│   │   │   ├── team-review.md    ← E(1) 的审核
│   │   │   ├── output/           ← 工人产出
│   │   │   ├── output-review.md  ← E(1) 的审核
│   │   │   └── final-report.md   ← D(1) 的最终报告
│   │   │
│   │   └── state.json
│   │
│   └── step-02-<slug>/
│       └── ...
```

### state.json 结构

```json
{
  "skill_version": "1.0",
  "task_summary": "<一句话任务描述>",
  "started": "<ISO timestamp>",
  "execution_mode": "inline",
  "max_depth": 5,
  "current_depth": 0,
  "overall_status": "in_progress",
  "phases": {
    "requirements": "done",
    "L0_plan": "in_progress",
    "L0_execution": "pending"
  },
  "steps": [
    {"slug": "step-01-...", "title": "...", "status": "pending", "depth": 0, "complexity": "leaf", "review": null}
  ],
  "overall_review_status": null,
  "questions_for_user": [],
  "errors": [],
  "heartbeat": "<ISO timestamp>"
}
```

`execution_mode`：简单任务 `inline`（主对话直接 spawn，等结果）；复杂/长耗时任务 `cron`（定时触发）。

### 上下文管理

每层智能体只读取它需要的最小文件集，防止上下文污染：

| 角色 | 读取文件 | 不读取 |
|------|---------|--------|
| C | requirements.md, state.json | 任何 plan-*.md（不受计划影响） |
| A(n) | 上级 plan-final.md, requirements.md, 下层 final-report.md（如有） | 兄弟步骤的文件、工人内部产出 |
| B(n) | plan-draft.md, requirements.md, 上级 plan-final.md | 同上 |
| D(n) | plan-final.md, team-config.md, 工人产出, state.json | 上级的 plan-draft/review（只看 final） |
| E(n) | plan-final.md, team-config.md, 工人产出, output-review.md | 同上 |
| 工人 | team-config.md, 任务描述（由 D 写入） | 其他工人的产出、上层审核意见 |

### 自动化机制

**方式 A — 单会话模式（inline）**：
- 执行树较浅（≤ 2 层）且总步数 ≤ 5 → 主对话直接 spawn Agent
- C 的问题在主对话中直接显示
- 每步完成后输出进度摘要

**方式 B — 多会话模式（cron）**：
- 执行树较深（≥ 3 层）或总步数 ≥ 6 或单步预计 ≥ 10min → 写入 cron 任务
- 主对话中注册 cron：每 20 分钟检查 state.json，取第一个待处理步骤 spawn Agent
- 心跳监控：每 2 小时检查停滞（heartbeat > 4h → 回退为 pending）
- 用户随时查看：`cat .recursive-planner/state.json` 或 `cat .recursive-planner/heartbeat.log`

**C 的主动联络**（v6.3 扩展）：
- state.json 中 `questions_for_user` 非空时 → C 在主对话中展示（经显著性过滤后）
- C 不再是"提问完就消失"——全程监控 state.json 状态，随时可能主动向你汇报关键进展或追问需求缺口
- C 的过滤原则：
  - **转达用户**：重要里程碑（计划通过、步骤完成、层级完成）、质量问题（连续驳回 ≥ 2 次）、阻塞（文件不可访问、子智能体超时）、skill 发现
  - **省略**：一般进度消息（"正在执行步骤 3/7"）、单次驳回后已修正、工人产出通过 D 验收
- 心跳日志中标记 `BLOCKED: awaiting user input`

### 失败处理

| 失败类型 | 处理 |
|---------|------|
| A(n) 连续 5 轮被 B(n) REJECT | B(n) 写根因分析 → 上报上级 B(n-1)，可能需重新定义该步骤的目标 |
| 工人团队连续 3 轮被 E(n) REJECT | E(n) 写根因分析 → 上报 D(n-1) + E(n-1)，建议重新规划 |
| 任一智能体产出文件为空/损坏 | 父级 D 检测到 → 重新 spawn 该智能体（最多 3 次）→ 仍失败则标记 `failed`，通知 C 转达用户 |
| Cron 任务丢失 | 下次心跳检测发现 → 重建 cron 任务（幂等） |
| 用户中途要求停止 | C 在 state.json 中标记 `overall_status: "cancelled"` → 所有 cron 任务检测到此状态后退出 |
| 子智能体超时（WAIT 过期） | D(n) 派生子智能体后等待超时（10 分钟无产出文件）。D(n) 重新 spawn（最多 3 次）→ 仍失败则标记 `failed`，通知 C 转达用户 |
| D/E 对整体完成判断不一致 | D 和 E 在联合检查时对某步骤是否通过存在分歧 → E 的判断优先。争议步骤标记为未完成，返回执行。若争议涉及 ≥ 3 步 → 上报上级 D(n-1)+E(n-1) 调解 |

### 本 Skill 自身的关键风险

| 风险 | 触发条件 | 处理 |
|------|---------|------|
| 递归深度失控 | 执行树深度 ≥ 5 层仍未到达叶子节点 | 强制停止递归。D(n) 将当前子树标记为"人工介入"，通过 C 通知用户：此步骤拆分深度超出自动化处理范围，请手动审查或重新定义任务边界 |
| C 提问疲劳 | C 与用户已连续交互 ≥ 6 轮，接近用户的耐心上限 | C 在下一轮提问时主动提示："已沟通 6 轮，是否暂停并重新思考方向？或跳过剩余次要问题，以当前信息先制定计划？"用户可选择继续、跳过剩余问题或暂停 |
| 文件污染 | `.recursive-planner/` 目录已存在（上次执行残留） | AI 启动本 skill 的 Step 0：检查 `.recursive-planner/` 是否存在 → 若存在，提示用户："检测到上次执行的残留文件。归档（移至 backup）还是删除？" 用户确认后继续 |
| 用户长期不响应 | cron 模式下，questions_for_user 非空但用户超过 48h 未回复 | 心跳日志标记 `STALE: user unresponsive > 48h`。下次用户与 AI 交互时，C 主动提醒："上次 recursive-planner 任务等待回复，要继续还是废弃？" |
| 跨角色上下文污染 | 某角色读取了不应读的文件，导致独立判断被污染 | 严格执行上下文管理中的读取权限表。每个角色的 Agent 提示中显式列出"可读文件"和"禁读文件"。Orchestrator 在 spawn 时仅传递允许的文件路径 |
| state.json 单点故障 | state.json 损坏，整个执行状态丢失 | Git 提交提供自然备份。若 state.json 损坏，从 `git show HEAD:.recursive-planner/state.json` 恢复。Orchestrator 每次写入前先写 `.bak` 备份 |
| C cron 模式下可用性缺口 | cron 模式下，C 的"持续监控"依赖 Orchestrator 定时触发，非按需响应 | 每次 cron 触发时，Orchestrator 先检查 questions_for_user[]（在其他步骤之前）。若有待处理消息，同步 spawn C 处理。最坏延迟 = cron 间隔。时间敏感的阻塞（超时、不可恢复 REJECT）→ C 写 heartbeat.log 并标记 URGENT |

### 依赖 Skill

- `general-task-flow`：用于判断任务是否需要升级到 recursive 模式
- `find_skills`：A/B/D/E 在计划/审核时搜索合适的工具

### 工具管理协议

A(n), B(n), D(n), E(n) 均可搜索和使用已有 skill/工具。需下载新工具时：
1. 子智能体 → 通报 C（写入 state.json 的 `questions_for_user[]`）
2. C → 向用户展示"需要下载 [工具名]，原因：[用途]"
3. 用户同意 → 下载
4. 用户拒绝 → 子智能体用已有工具替代方案

工人团队使用的工具由 D(n) 和 E(n) 在 `team-config.md` 中配置，E(n) 审核。同样遵守"下载需用户批准"规则。

### Skill 主动搜索机制（v6.3 新增）

所有智能体（A/B/D/E）在开始工作前**必须**调用 `find_skills` 搜索可用 skill：

- **A** 在制定计划前搜索 —— 是否有领域专用 skill 可提升计划质量？搜索 2-3 种关键词变体，发现的 skill 向 C 汇报
- **B** 在审核计划时搜索 —— A 是否遗漏了可用的 skill？B 自己也必须搜索以二次确认，发现遗漏时写入 REJECT 理由（第 9 条审核标准：skill 利用）
- **D** 在为工人配置工具时搜索 —— 每个工人是否有最匹配的已有 skill？对每个工人独立搜索，使用工人任务专用的关键词
- **E** 在审核团队配置时检查 —— D 是否为每个工人搜索了 skill？分配的 skill 是否最匹配？D 跳过搜索时 E 必须 MODIFY

发现的 skill 通过 C 汇报给你审批下载。你不会被强制安装任何 skill——审批权始终在你手中。
