# Self-Authored Compliance Programs — The AI Writes a Branching Checker, and the Checker Halts It

> **Status: unformed.** Captured as a rough direction, not a settled position. The mechanism below is plausible; the failure analysis is the part that most needs work.

**One sentence**: Rather than having the AI judge compliance in-context with its own language-model judgment, have it *autonomously author a branching decision structure*, compile that into a real computer program (狭义 — an actual program, not a prompt), and run it; on violation, **all actions halt**.

## The Move

The proposed loop:

```
AI authors a branching decision structure  →  it becomes an executable program
                                           →  the program runs against the action
                                           →  violation  →  HALT ALL ACTIONS
```

The critical word is 狭义 — *narrow-sense* computer program. The verdict must come from **symbolic execution**, not from the model deciding. That single choice is what the idea rests on.

## Why Program-Mediated Judgment Beats In-Context Judgment

| Property | In-context model judgment | Executed program |
|---|---|---|
| Determinism | Sampling-dependent; same input can give different verdicts | Same input, same verdict, every time |
| Auditability | No artifact — you can only re-prompt and hope | A reviewable object exists after the fact |
| Separation | The judge is the actor, in the actor's own context | Runs as a separate artifact |
| Exactness | Approximate | Exact |
| Cost at scale | One model call per check | Cheap, repeatable |

The deepest of these is **judgment moved from runtime to authoring time**. The model contributes judgment once, when deciding *what the relevant conditions are*. After that, the verdict is mechanical. You pay for judgment once instead of on every action, and you get a stable criterion instead of a per-instance opinion.

The halt semantics matter too: "停止一切行动" is a **hard stop**, not a soft one. A model *told* to stop can be argued out of it; a program that refuses to return control cannot. This is the difference between a rule and a circuit breaker — and only the latter is a guarantee. (See [[harness-structure-enforcement]] — the halt is harness authority, not model discretion.)

## The Central Weakness: A Self-Authored Checker Is Self-Serving

The obvious attack: an agent that authors its own compliance program can author one that always returns "compliant." If the checker is generated by the same entity whose actions it governs, it is not a check — it is theater.

The design distinction that matters is **rule-derived vs. act-derived**:

- **Act-derived** — the AI writes a checker for *"is this particular action OK?"* This is where gaming hides: the checker is shaped around the act it is meant to catch.
- **Rule-derived** — the AI writes a checker for the *rule set*, independently of any specific action. Reusable, and reviewable *against the rule text* rather than against an outcome.

Rule-derived checkers are far harder to game, because the checker can be diffed against the rule it claims to implement. That gives a review surface that in-context judgment never has.

Two further mitigations worth exploring:

- **Separate the authoring context from the acting context** — a fresh instance that doesn't know the specific action is about to be taken.
- **Asymmetric authority** — the program can only *block*, never *permit*. It is a floor, not a certificate. The harness retains its own independent veto.

## Qualification: Not Every Rule Is Checkable

There is a ceiling here, and it is the same ceiling as [[audit-blind-spot-spec-limitation]]: spec-based checking can only find gaps between the action and the spec — it cannot find gaps *in the spec itself*. A compliance program encodes the rules you named, and is blind to the rules you didn't.

So this mechanism is real and useful for *checkable* rules (access bounds, resource limits, prohibited operations, schema constraints), and structurally silent on the class of harms nobody wrote down. It should not be mistaken for a complete safety story.

This is also the [[structure-native-tools]] pattern in safety clothing: the learning tool is approximate, the symbolic tool is exact, and the guarantee lives in the symbolic stage. The compliance program *is* that stage.

## Open Questions

- **What language does the AI author in?** A general-purpose language is maximally expressive and minimally reviewable; a restricted rule DSL is the reverse. Where on that spectrum does this actually work?
- **Who reviews the checker?** If the program is the artifact that makes auditing possible, what audits the audit — human review, a second model, a meta-checker?
- **What does "halt" mean operationally?** Stop the current episode, lock the agent out, escalate to a human? An irreversible halt is a safety guarantee and an availability risk at once.
- **Does the branching structure need to be a tree?** "分支结构" suggests a decision tree; a general program with state and loops may be needed, or the tree may be a deliberate restriction for reviewability.
- **How does this relate to the rules being incomplete?** The mechanism governs the rules it is given. Who owns the gap?
